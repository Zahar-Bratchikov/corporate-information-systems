# Отчёт по проектированию хранилища данных КИС

## ИС УПЗ IT — Информационная система управления проектами и задачами в IT

---

## 1. Постановка задачи

### 1.1. Описание назначения КИС и основного функционала согласно ТЗ

**Назначение КИС:** Программное изделие предназначено для IT-подразделений организаций: команды разработки ПО, отделы информационных технологий, проектные команды по внедрению и сопровождению информационных систем. Система обеспечивает планирование и учёт IT-проектов (разработка и внедрение ПО, сервисов, доработки), управление задачами разработки (фичи, исправления, технические задачи), распределение нагрузки между разработчиками и тестировщиками, контроль сроков и формирование отчётности для руководства и стейкхолдеров.

**Основной функционал по ТЗ:**

- Редактирование данных: создание, изменение и удаление записей по IT-проектам (наименование, код, ответственный, даты релиза), задачам (название, тип — фича/баг/задача, приоритет, срок, статус), исполнителям (пользователи и роли), справочникам статусов и приоритетов, спринтам/итерациям; назначение исполнителей на задачи, привязка задач к проектам и спринтам; валидация вводимых данных.
- Генерация пяти отчётов с выводом в MS Word, MS Excel, PDF: сводный по IT-проектам; задачи исполнителя с итогами; просроченные задачи с вычисляемым полем «дни просрочки»; загрузка команды по статусам; статусы IT-проектов с агрегатами и процентом выполнения.
- Авторизованный доступ по ролям (Администратор, Руководитель проекта/Тимлид, Разработчик/QA, Наблюдатель), вход по логину и паролю.

Хранилище данных КИС должно обеспечивать хранение и согласованность данных, необходимых для реализации указанного функционала.

### 1.2. Цель работы и задачи

**Цель работы:** спроектировать хранилище данных КИС ИС УПЗ IT: описать предметную область, построить логическую и физическую модели БД, реализовать БД в СУБД и заполнить тестовыми данными.

**Задачи:**

1. Описать предметную область с выделением основных сущностей и связей между ними.
2. Построить логическую модель БД (ER-диаграмма) с названиями сущностей и полей на русском языке.
3. Построить физическую модель БД (ER-диаграмма) с читаемыми именами, обосновать выбор типов полей и описать назначение таблиц.
4. Реализовать БД в СУБД (PostgreSQL) и заполнить тестовыми данными (не менее 5 записей в каждой таблице).
5. Оформить отчёт с демонстрацией содержимого таблиц и выводами.

## 2. Предметная область проектируемой БД (подробнее расписать, что бы сущности и связи вытекали из описания)

**Предметная область** — планирование и учёт IT-проектов и задач в рамках IT-подразделения: проекты (продукты, сервисы, релизы), задачи (фичи, баги, технические задачи), исполнители (пользователи с ролями), спринты/итерации, сроки и статусы.

### Основные сущности

1. **Роль** — тип прав пользователя в системе (Администратор, Руководитель проекта/Тимлид, Разработчик/QA, Наблюдатель и т.п.). Определяет, какие операции и отчёты доступны пользователю.
2. **Пользователь** — сотрудник, работающий в системе: логин для входа, хеш пароля, ФИО и связь с одной ролью. Пользователь может выступать ответственным за проекты и исполнителем по задачам.
3. **Проект** — IT-проект (продукт, сервис, доработка): наименование, уникальный код, планируемая дата релиза, ответственный (ссылка на пользователя).
4. **Тип задачи** — классификация задачи: фича, баг, техническая задача, доработка, исследование и т.д.
5. **Статус задачи** — этап жизненного цикла задачи: новая, в работе, в тестировании, выполнена, отложена.
6. **Приоритет** — степень срочности задачи: низкий, средний, высокий, критический, блокер.
7. **Спринт** — итерация разработки с фиксированными датами начала и окончания; принадлежит одному проекту. Задачи могут быть привязаны к спринту.
8. **Задача** — единица работы: название, срок выполнения, тип, приоритет, статус; привязка к проекту, к спринту (опционально) и к исполнителю (опционально).

### Связи между сущностями

- **Пользователь — Роль:** каждый пользователь имеет ровно одну роль (многие к одному).
- **Проект — Пользователь:** у проекта может быть один ответственный (руководитель проекта), связь многие к одному, опционально.
- **Спринт — Проект:** спринт принадлежит одному проекту (многие к одному).
- **Задача — Тип задачи:** у задачи один тип (многие к одному).
- **Задача — Приоритет:** у задачи один приоритет (многие к одному).
- **Задача — Статус задачи:** у задачи один статус (многие к одному).
- **Задача — Проект:** задача входит в один проект (многие к одному).
- **Задача — Спринт:** задача может быть привязана к одному спринту или не привязана (многие к одному, опционально).
- **Задача — Пользователь:** у задачи может быть один исполнитель (многие к одному, опционально).

Данная структура позволяет реализовать по ТЗ редактирование проектов и задач, назначение исполнителей, привязку к спринтам и формирование всех пяти отчётов (агрегаты по проектам, по исполнителям, просроченные задачи, загрузка по статусам, статусы проектов).

## 3. Логическая модель

Логическая модель представлена в виде ER-диаграммы с сущностями и атрибутами на русском языке. Названия сущностей и полей читаемые.

**Файл диаграммы:** [диаграмма](logical_model.drawio.png)

### Сущности и атрибуты (логическая модель)


| Сущность          | Атрибуты (поля)                                                                                                                                                          |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Роль**          | Код_роли (PK), Наименование_роли                                                                                                                                         |
| **Пользователь**  | Код_пользователя (PK), Логин, Хеш_пароля, ФИО, Код_роли (FK)                                                                                                             |
| **Проект**        | Код_проекта (PK), Наименование, Код_проекта_внешний, Дата_релиза, Код_ответственного (FK)                                                                                |
| **Тип_задачи**    | Код_типа_задачи (PK), Наименование_типа                                                                                                                                  |
| **Статус_задачи** | Код_статуса (PK), Наименование_статуса                                                                                                                                   |
| **Приоритет**     | Код_приоритета (PK), Наименование_приоритета                                                                                                                             |
| **Спринт**        | Код_спринта (PK), Наименование_спринта, Дата_начала, Дата_окончания, Код_проекта (FK)                                                                                    |
| **Задача**        | Код_задачи (PK), Название_задачи, Срок_выполнения, Код_типа_задачи (FK), Код_приоритета (FK), Код_статуса (FK), Код_проекта (FK), Код_спринта (FK), Код_исполнителя (FK) |


Связи: Пользователь → Роль; Проект → Пользователь (ответственный); Спринт → Проект; Задача → Тип_задачи, Приоритет, Статус_задачи, Проект, Спринт, Пользователь (исполнитель).

## 4. Физическая модель

Физическая модель реализована в СУБД PostgreSQL. Имена таблиц и столбцов — читаемые (латиница, принятые в практике имена).

**Файл диаграммы:** [диаграмма](ERD-shema.pgerd).

### Соответствие логической и физической моделей


| Логическая сущность | Физическая таблица |
| ------------------- | ------------------ |
| Роль                | `roles`            |
| Пользователь        | `users`            |
| Проект              | `projects`         |
| Тип_задачи          | `task_types`       |
| Статус_задачи       | `task_statuses`    |
| Приоритет           | `priorities`       |
| Спринт              | `sprints`          |
| Задача              | `tasks`            |


### Обоснование выбора типов полей

- **Целочисленные ключи:** `INTEGER` для справочников с небольшим числом записей (`roles.id`); `SERIAL` (автоинкремент) для основных таблиц — удобно для связей и индексов.
- **Строки переменной длины:** `VARCHAR(n)` с ограничением длины под содержание: логин и коды — 50–100 символов, названия и ФИО — 200–300, название задачи — 500; ограничение длины защищает от некорректного ввода и задаёт разумный размер полей.
- **Пароль:** `VARCHAR(255)` — достаточная длина для хранения криптографического хеша (например, bcrypt).
- **Даты:** `DATE` для сроков выполнения, дат релиза и границ спринтов — без времени, что соответствует бизнес-требованиям.
- **Внешние ключи:** `INTEGER` в соответствии с типом первичных ключей ссылочных таблиц; для опциональных связей (ответственный, спринт, исполнитель) допускается NULL.

### Назначение сущностей (таблиц) БД


| Таблица           | Назначение                                                                                                                                          |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| **roles**         | Справочник ролей пользователей для разграничения доступа (Администратор, Руководитель, Разработчик/QA, Наблюдатель и др.).                          |
| **users**         | Пользователи системы: учётные записи (логин, хеш пароля), ФИО и роль; используются как ответственные по проектам и исполнители по задачам.          |
| **projects**      | IT-проекты: наименование, код, дата релиза, ответственный; основа для привязки задач и спринтов и для отчётов по проектам.                          |
| **task_types**    | Справочник типов задач (фича, баг, техническая задача и т.д.) для классификации и отчётов.                                                          |
| **task_statuses** | Справочник статусов задач (новая, в работе, в тестировании, выполнена и т.д.) для отображения этапа и агрегации в отчётах.                          |
| **priorities**    | Справочник приоритетов задач для сортировки и фильтрации.                                                                                           |
| **sprints**       | Спринты/итерации с датами начала и окончания; привязка к проекту; опциональная привязка задач к спринту для отчёта по загрузке команды.             |
| **tasks**         | Задачи: название, срок, тип, приоритет, статус, проект, спринт, исполнитель; центральная сущность для учёта работ и формирования всех пяти отчётов. |

## 6. Вывод

### 6.1. Что сделано

- Сформулирована постановка задачи проектирования хранилища данных КИС в соответствии с ТЗ на ИС УПЗ IT.
- Подробно описана предметная область с выделением восьми основных сущностей (Роль, Пользователь, Проект, Тип задачи, Статус задачи, Приоритет, Спринт, Задача) и связей между ними.
- Построена логическая модель БД в виде ER-диаграммы (PlantUML) с названиями сущностей и полей на русском языке.
- Построена физическая модель БД в виде ER-диаграммы с читаемыми именами таблиц и полей; приведено обоснование выбора типов данных и описано назначение каждой таблицы.
- Реализована БД в СУБД PostgreSQL: созданы таблицы, ограничения и индексы (файлы schema.sql, seed.sql).
- Заполнена тестовыми данными: во всех таблицах не менее 5 записей (в части таблиц — 6 и более для реалистичности).
- Оформлен отчёт по заданной структуре с демонстрацией содержимого таблиц.

### 6.2. Плюсы и минусы, что реализовано и что не выполнено

**Плюсы:**

- Модель покрывает все сущности и связи, необходимые для заявленного в ТЗ функционала (редактирование проектов и задач, назначение исполнителей, спринты, пять отчётов).
- Нормализация: справочники вынесены в отдельные таблицы, дублирование данных минимизировано.
- Использованы ограничения целостности (PRIMARY KEY, FOREIGN KEY, UNIQUE, CHECK для дат спринта), что повышает надёжность данных.
- Добавлены индексы по полям, участвующим в отборах и соединениях (проект, исполнитель, статус, срок задачи), что способствует быстрой работе отчётов.
- Типы полей обоснованы с учётом объёма и характера данных.

**Минусы и ограничения:**

- Хеши паролей в seed.sql — заглушки; 
- Не реализованы триггеры и представления (VIEW) для отчётов; их можно добавить на этапе реализации приложения.

**Реализовано полностью:** постановка задачи, описание предметной области, логическая и физическая модели, реализация БД в PostgreSQL, тестовые данные (≥5 записей в каждой таблице), структура отчёта и выводы.
