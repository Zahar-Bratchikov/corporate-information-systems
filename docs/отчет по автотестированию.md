# Отчёт по результатам автоматизированного тестирования ИС УПЗ IT

## 1. Постановка задачи

### 1.1. Описание назначения КИС и основного функционала согласно ТЗ

Согласно техническому заданию (в т.ч. `docs/specifications.md`), **информационная система управления проектами и задачами в IT (ИС УПЗ IT)** предназначена для IT-подразделений: планирование и учёт IT-проектов и релизов, управление задачами, распределение нагрузки между исполнителями, контроль сроков и формирование отчётности.

**Основной функционал по ТЗ:**

- ведение данных по **IT-проектам**, **задачам**, **пользователям** и ролям, **спринтам**, справочникам (типы задач, статусы, приоритеты);
- **авторизованный доступ** с разграничением прав (администратор, руководитель проекта / тимлид, разработчик / QA, наблюдатель);
- **не менее пяти видов отчётов** с выгрузкой в **MS Excel (.xlsx), MS Word (.docx), PDF**;
- **валидация данных** и корректная реакция на ошибочный ввод и несанкционированный доступ.

Подробное описание эндпоинтов API приведено в `docs/API.md`.

### 1.2. Цель работы и задачи, которые нужно выполнить для достижения цели

**Цель:** подтвердить соответствие реализованной ИС УПЗ IT требованиям ТЗ за счёт автоматизированной проверки ключевых сценариев: вход в систему, работа под разными ролями, изменение данных через UI и API, формирование отчётов (превью и файлы), негативные сценарии.

**Задачи:**

1. Зафиксировать **вид тестирования** и порядок проведения (инструменты, исполнители).
2. Сопоставить разделы отчёта о тестировании с **файлами автотестов** и **реализацией в приложении**.
3. По итогам описать **что покрыто тестами**, **результаты** и **направления доработки**.

## 2. Реализация

### 2.1. Вид тестирования и кто проводит тестирование

| Аспект | Содержание |
|--------|------------|
| **Виды** | Сквозное (E2E) тестирование веб-интерфейса; контрактное / интеграционное тестирование REST API; модульные тесты клиента (Vitest) для отдельных слоёв |
| **Инструменты** | **Playwright Test** (`frontend/e2e/`) — UI и API; **Vitest** + Testing Library — `frontend/src/**/*.test.ts(x)` |
| **Исполнение** | Локально: `npm run test:e2e` (и unit-тесты) в каталоге `frontend`; в CI — workflow **GitHub Actions** (`.github/workflows/playwright.yml`), если он настроен в репозитории |
| **Кто проводит** | Тесты выполняются **автоматически**; запуск инициирует разработчик или проверяющий; интерпретация HTML-отчёта Playwright (`npx playwright show-report`) — человеком |

**Оформление полей тест-кейса по ТЗ** в части E2E/API: функции `annotateTzCase` и `annotateTzPassed` в `frontend/e2e/helpers/tz-metadata.ts` добавляют в отчёт Playwright аннотации «Тестируемая функция», «Входные данные», «Ожидаемые результаты», «Фактический результат».

### 2.2. Тестирование основного функционала

#### 2.2.1. Авторизация

**Автотесты:** `frontend/e2e/ui/tz-auth.spec.ts`, `frontend/e2e/api/auth.api.spec.ts`.

Проверяется:

- успешный вход **администратора**, **руководителя проекта**, **разработчика**, **наблюдателя** (отображение оболочки приложения, для админа — ФИО и роль);
- отказ при **неверном пароле** и **несуществующем логине** (сообщение об ошибке, остаток на `/login`);
- **выход** из системы и редирект на логин при попытке открыть `/projects` без сессии;
- **защита маршрутов** без JWT.

**Реализация в приложении:** страница `frontend/src/pages/Login.tsx` (или эквивалент), селекторы `data-testid` с префиксом `upzit-` (`upzit-login-username`, `upzit-login-password`, `upzit-login-submit`, `upzit-login-error` и др.); после успешного `POST /api/authentication/login` — сохранение токена и профиля, переход в `upzit-app-shell`.

**API:** пустое тело логина → **400**; неизвестные учётные данные → **401** с полем `error`; корректный вход сидера `admin` → **200**, JWT и `roleName`; алиас `POST /api/auth/login` поддерживается.

#### 2.2.2. Функционал (вид) ИС под разными пользователями

**Автотесты:** `frontend/e2e/ui/tz-auth.spec.ts` (фрагменты по ролям и меню), `frontend/e2e/ui/tz-roles-navigation.spec.ts`.

Проверяется:

- редирект с **`/`** на **`/projects`** после входа;
- переключение разделов меню: задачи, пользователи, спринты, отчёты, проекты (видимость страниц по `data-testid`);
- обработка **несуществующего URL**;
- у **администратора** — доступ к таблице пользователей;
- у **разработчика** — отсутствие пункта «Пользователи» и экран «Доступ запрещён» при прямом переходе на `/users`;
- у **наблюдателя** — отсутствие кнопки добавления проекта;
- у **руководителя** — пункт «Пользователи» в меню есть, но страница управления пользователями для не-админа недоступна (задокументировано комментарием в тесте).

**Реализация в приложении:** макет с боковым меню (`Layout`), условный рендер пунктов и кнопок по роли (`canEdit`, `isAdmin` и т.п.), страницы с `upzit-*-page` test id.

**Дополнительно по API справочников:** `frontend/e2e/api/reference-data.api.spec.ts` — анонимный доступ к ролям, **401** без токена для типов задач при необходимости, **200** с токеном наблюдателя.

#### 2.2.3. Редактирование информационной составляющей БД

**Автотесты (UI):** `frontend/e2e/ui/tz-crud.spec.ts` (serial-группа).

Проверяется:

- **создание проекта** под руководителем (форма модального окна, появление строки в таблице);
- **редактирование наименования** проекта и сохранение в таблице и при повторном открытии формы;
- **дубликат кода проекта** в UI — сообщение об ошибке в форме;
- **создание задачи** с заголовком;
- **просмотр спринтов** у администратора.

**Автотесты (API):** `frontend/e2e/api/projects.api.spec.ts`, `frontend/e2e/api/tasks.api.spec.ts`.

- Список проектов **GET** — **200**, непустой массив;
- **GET** несуществующего проекта — **404**;
- **POST** создание проекта от разработчика — **403**; от руководителя — **201**;
- **POST** с дублирующим кодом — **400** с `error`;
- **GET** задач без авторизации — **401**; с токеном — массив задач.

**Реализация в приложении:** страницы «Проекты», «Задачи», «Спринты» с формами и таблицами; обращения к `/api/projects`, `/api/tasks`, `/api/sprints`, справочникам. Изменения данных отражаются в БД PostgreSQL (схема `database/init/01-schema.sql`).

#### 2.2.4. Отчёты

**Показать реализацию в самом приложении**

Страница **«Отчёты»** (`frontend/src/pages/Reports.tsx`): блоки отчётов, кнопки превью (`upzit-report-preview-*`), скачивание Excel/PDF (`upzit-report-it-projects-summary-xlsx` и др.), выбор исполнителя для отчёта по задачам. Превью загружается с эндпоинтов `/api/reports/previews/...` (JSON для UI).

**Показать реализацию в файле (файлах), в который выводится информация**

- **UI-тесты** (`frontend/e2e/ui/tz-reports.spec.ts`): после клика по кнопке скачивания Playwright фиксирует событие `download` — проверяются **расширение** (`.xlsx`, `.pdf`) и для Excel — **ненулевой размер** временного файла на диске.
- **API-тесты** (`frontend/e2e/api/reports.api.spec.ts`): **GET** с JWT — код **200**, заголовки `Content-Type` (`spreadsheet` для xlsx, `pdf` для PDF, `wordprocessingml` для docx), **ненулевое тело** ответа; превью — JSON с массивом `rows`; **неполный запрос** отчёта по исполнителю без `assigneeId` — **400**.

Перечень путей отчётов и форматов — в `docs/API.md` (раздел «Отчёты»).

#### 2.2.5. Реакция ИС на ошибочный ввод данных

**Автотесты:** `frontend/e2e/ui/tz-validation.spec.ts`, фрагменты `tz-auth.spec.ts` (неверный логин/пароль), `tz-crud.spec.ts` (дубликат кода проекта), `frontend/e2e/api/auth.api.spec.ts`, `projects.api.spec.ts`, `tasks.api.spec.ts`, `reports.api.spec.ts` (отчёт без обязательного параметра).

Проверяется:

- **HTML5-валидация** формы логина при пустом логине;
- **задача с пробелами в названии** (после trim пусто) — ошибка в форме в UI; **пустой title** в API — **400**;
- **дубликат кода проекта** — сообщение в UI и **400** в API;
- **отчёт без assigneeId** — **400**.

**Реализация в приложении:** блоки `upzit-login-error`, `upzit-project-form-error`, `upzit-task-form-error`; на backend — валидация моделей и бизнес-правил, коды **400**, **401**, **403**, **404** согласно сценарию.

## 3. Вывод

### 3.1. Что сделано

Реализован **набор автотестов** на базе **Playwright** (каталог `frontend/e2e/`): **8 файлов** сценариев — **5 UI-спецификаций** (`tz-auth`, `tz-roles-navigation`, `tz-crud`, `tz-reports`, `tz-validation`) и **5 API-спецификаций** (`auth`, `projects`, `tasks`, `reports`, `reference-data`). Для части тестов используется унифицированное **оформление метаданных ТЗ** (`tz-metadata.ts`). Дополнительно во фронтенде есть **модульные тесты** Vitest (`Login.test.tsx`, `Tasks.test.tsx`, `api.test.ts`, `endpoints.test.ts`).

### 3.2. Анализ результатов тестов

- **Охват:** последовательно проверяются **аутентификация**, **навигация и различия ролей**, **CRUD проектов/задач и просмотр спринтов**, **превью и выгрузка отчётов** (включая несколько форматов на уровне API), **негативные сценарии** на UI и API.
- **Соответствие ожиданиям:** при **успешном** прогоне все assertion’ы Playwright выполняются; в аннотациях фиксируется **фактический результат** через `annotateTzPassed`. При **падении** теста диагностика выполняется по логам прогона, trace и HTML-отчёту Playwright.
- **Ограничения покрытия:** не все пять отчётов и все комбинации форматов могут быть проверены в UI в одном наборе (часть проверок вынесена в API); сценарии канбана, массового удаления и полный перечень кейсов из `docs/TEST_CASES.md` могут требовать **ручной** или **дополнительной** автоматизации.

### 3.3. Обозначение дальнейших действий

1. Расширить E2E по оставшимся пунктам `docs/TEST_CASES.md` (канбан, подтверждения удаления, все форматы каждого отчёта в UI).
2. Поддерживать **зелёный CI**: при изменении API или сидеров БД синхронно обновлять ожидания в тестах.
3. По необходимости добавить **нагрузочное** или **регрессионное** тестирование вне рамок текущего набора Playwright.
