
## 1. Постановка задачи

### 1.1. Описание назначения КИС и основного функционала согласно ТЗ

Согласно техническому заданию (файл `docs/specifications.md`), **информационная система управления проектами и задачами в IT (ИС УПЗ IT)** предназначена для применения в IT-подразделениях: планирование и учёт IT-проектов и релизов, управление задачами (фичи, исправления, технические задачи), распределение нагрузки между исполнителями, контроль сроков и формирование отчётности.

**Основной функционал по ТЗ:**

- ведение данных по **IT-проектам**, **задачам**, **пользователям** и ролям, **спринтам**, справочникам (типы задач, статусы, приоритеты), назначение исполнителей, привязка задач к проектам и спринтам;
- **авторизованный доступ** с разграничением прав по ролям: администратор, руководитель проекта / тимлид, разработчик / QA, наблюдатель;    
- **не менее пяти отчётов** с выгрузкой в форматы **MS Excel (.xlsx), MS Word (.docx), PDF** в соответствии с перечнем в ТЗ;
- **валидация данных** и реакция на ошибочный ввод и несанкционированный доступ;
- эксплуатация в корпоративной среде с возможностью **развёртывания в Docker**.

Подробное описание отчётов и полей приведено в разделе 4.1 ТЗ (`docs/specifications.md`).

### 1.2. Цель работы и задачи для её достижения

**Цель работы:** спроектировать и реализовать работоспособный программный комплекс ИС УПЗ IT в соответствии с ТЗ: клиент-серверная архитектура, реляционная БД, веб-интерфейс, REST API, отчёты в файловых форматах, разграничение доступа.

**Задачи:**

1. Разработать и применить **модель данных** (схема БД, связи сущностей).
2. Реализовать **backend** — REST API, бизнес-логика, авторизация (JWT), проверка прав, формирование отчётов.
3. Реализовать **frontend** — SPA: вход, работа с проектами, задачами, пользователями, спринтами, отчётами; удобный и тестируемый интерфейс.
4. Обеспечить **развёртывание** через Docker Compose (БД, API, статика фронтенда).
5. Подготовить **документацию** API и рекомендации по тестированию; по возможности — unit-тесты.

## 2. Реализация

### 2.1. Средства, среда разработки и используемые фреймворки

| Компонент           | Технологии                                                                                                                                                                          |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **База данных**     | PostgreSQL 16, скрипт инициализации `database/init/01-schema.sql`                                                                                                                   |
| **Backend**         | C#, **.NET 8**, **ASP.NET Core Web API**, Entity Framework Core, JWT (Bearer), BCrypt для хешей паролей; библиотеки для отчётов: ClosedXML (Excel), QuestPDF (PDF), Open XML (Word) |
| **Frontend**        | **TypeScript**, **React 18**, **Vite**, **React Router v6**; обращение к API через `fetch`                                                                                          |
| **Контейнеризация** | **Docker**, **Docker Compose** (`docker-compose.yml`): сервисы `db`, `backend`, `frontend` (сборка SPA + nginx)                                                                     |
| **Тестирование**    | Backend: xUnit, Moq (`backend/UpzIt.Api.Tests`); Frontend: **Vitest**, Testing Library; **E2E и API**: **Playwright** (`frontend/e2e/`), сценарии увязаны с `docs/TEST_CASES.md` и разделами отчёта по ТЗ |
| **Документация**    | `docs/API.md`, `docs/TEST_CASES.md`, `README.md`; отчёт о разработке — этот файл                                                                                                                                      |

Исходный код: `backend/` (проект `UpzIt.Api`), `frontend/` (Vite-приложение), `database/init/`.

### 2.1.1. Автоматизированное тестирование по структуре учебного ТЗ

**Вид тестирования:** сквозное (E2E) и контрактное тестирование REST API с помощью **Playwright Test**; прогон в CI — **GitHub Actions** (workflow `.github/workflows/playwright.yml`).

**Кто проводит:** выполняется автоматически на машине разработчика (`npm run test:e2e` в каталоге `frontend`) и на серверах GitHub при push/PR; инициатор — разработчик/преподаватель при проверке.

**Оформление тест-кейса в коде** (требования ТЗ к отчёту о тестировании):

| Поле ТЗ | Где фиксируется в автотестах |
|--------|------------------------------|
| Тестируемая функция | Аннотация `Тестируемая функция` + имя теста |
| Входные данные | Аннотация `Входные данные` (учётки, поля форм, URL API) |
| Ожидаемые результаты | Аннотация `Ожидаемые результаты` |
| Фактический результат | Аннотация `Фактический результат` при успешном прохождении; при падении — статус failed и вложения/trace в отчёте Playwright |
| Комментарии | Аннотация `Комментарий` (при необходимости) |

Реализация: `frontend/e2e/helpers/tz-metadata.ts` (функции `annotateTzCase`, `annotateTzPassed`). Метаданные видны в **HTML-отчёте** Playwright (`npx playwright show-report`).

**Соответствие разделам отчёта:**

| Раздел отчёта (ТЗ) | Файлы автотестов |
|--------------------|------------------|
| § 2.2.1 Авторизация | `e2e/ui/tz-auth.spec.ts`, `e2e/api/auth.api.spec.ts` |
| § 2.2.2 Вид ИС под разными пользователями, навигация | `e2e/ui/tz-roles-navigation.spec.ts` |
| § 2.2.3 Редактирование данных (БД) | `e2e/ui/tz-crud.spec.ts`, часть API в `e2e/api/*.api.spec.ts` |
| § 2.2.4 Отчёты (UI + файлы) | `e2e/ui/tz-reports.spec.ts`, `e2e/api/reports.api.spec.ts` |
| § 2.2.5 Ошибочный ввод | `e2e/ui/tz-validation.spec.ts`, `e2e/api/tasks.api.spec.ts`, `e2e/api/projects.api.spec.ts` |

**Реализация в приложении** для отчётов: страница «Отчёты» (`frontend/src/pages/Reports.tsx`), выгрузка файлов через `apiBlob` и эндпоинты `/api/reports/...`. **Реализация в файлах:** скачанные `.xlsx`, `.docx`, `.pdf` проверяются в UI-тестах (имя файла, размер) и в API-тестах (заголовки `Content-Type`, размер тела ответа).

## 3. Вывод

### 3.1. Что сделано

Реализована **ИС УПЗ IT** в объёме, заявленном в репозитории: **PostgreSQL**, **ASP.NET Core 8 API** с JWT и ролями, **React SPA**, **пять видов отчётов** с экспортом в Excel, Word и PDF, **Docker Compose** для запуска всего стека.

### 3.2. Плюсы и минусы; полнота реализации

**Плюсы:**

- чёткое разделение frontend / backend / БД;
- соответствие ТЗ по ролям, CRUD, отчётам и форматам;
- документированное API и тестовые селекторы UI;
- возможность развернуть в docker

**Минусы и ограничения:**

- покрытие автотестами не исчерпывает все строки `docs/TEST_CASES.md` (например, часть сценариев удаления и канбан остаётся для ручной проверки);
- нет поддержки **HTTPS** в учебном стенде.

**Анализ результатов автотестов:** прогон Playwright объединяет проверки авторизации, ролей, CRUD в UI, выгрузки отчётов и негативных сценариев; при успешном завершении job в GitHub Actions или локально `npm run test:e2e` фактический результат совпадает с ожидаемым в аннотациях. При сбое анализ выполняется по HTML-отчёту, trace и логам `docker compose`.

**Итог по ТЗ:** основной функционал реализован и частично зафиксирован автотестами с оформлением полей по ТЗ.

### 3.3. Дальнейшие действия

1. Расширить Playwright-сценарии по оставшимся кейсам из `docs/TEST_CASES.md` (канбан, удаление с подтверждением, все форматы каждого отчёта).
2. Настроить **HTTPS** и секреты JWT для production, вынести конфигурацию в переменные окружения.
3. **PWA**, уведомления о дедлайнах, расширенный аудит действий пользователей; при необходимости — доработать разбор `errors` из ответа 400 API на фронте для более понятных сообщений в формах.
