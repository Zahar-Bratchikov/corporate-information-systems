# Тест-кейсы ИС УПЗ IT

Документ описывает сценарии приёмочного и регрессионного тестирования веб-приложения (React + ASP.NET Core + PostgreSQL), развёрнутого по инструкции из `README.md` (Docker, URL `http://localhost:18080`).

**Тестовые учётные записи** (пароль у всех: `password`):

| Логин       | Роль                          |
|------------|-------------------------------|
| admin      | Администратор                 |
| pm_sidorov | Руководитель проекта / Тимлид |
| dev_kozlov | Разработчик / QA              |
| qa_novikova| Разработчик / QA              |
| dev_petrov | Разработчик / QA              |
| viewer     | Наблюдатель                   |

## 1. Авторизация и сессия

### TC-AUTH-001. Успешный вход администратора

| Поле | Значение |
|------|----------|
| **Предусловия** | Сервисы `docker compose up` запущены; БД инициализирована, сидер выполнен. |
| **Шаги** | 1. Открыть в браузере `http://localhost:18080`.<br>2. Убедиться, что отображается страница входа (поля логин, пароль).<br>3. Ввести логин `admin`, пароль `password`.<br>4. Нажать кнопку входа (или аналог). |
| **Ожидаемый результат** | Запрос `POST /api/auth/login` завершается успешно (код 2xx). Пользователь перенаправлен в приложение. В шапке отображаются ФИО и роль «Администратор» (или эквивалент из сидера). Доступны разделы: Проекты, Задачи, Пользователи, Спринты, Отчёты. |

### TC-AUTH-002. Успешный вход руководителя проекта

| Поле | Значение |
|------|----------|
| **Предусловия** | Как в TC-AUTH-001. |
| **Шаги** | 1. Открыть страницу входа.<br>2. Ввести `pm_sidorov` / `password`.<br>3. Выполнить вход. |
| **Ожидаемый результат** | Успешная авторизация. В шапке — роль руководителя/тимлида. В меню есть «Пользователи» (для роли менеджера по реализации). Доступны Проекты, Задачи, Спринты, Отчёты. |

### TC-AUTH-003. Успешный вход разработчика

| Поле | Значение |
|------|----------|
| **Предусловия** | Как в TC-AUTH-001. |
| **Шаги** | 1. Войти под `dev_kozlov` / `password`. |
| **Ожидаемый результат** | Успешный вход. Пункт «Пользователи» в навигации **отсутствует**. Остальные разделы из роли доступны (Проекты, Задачи, Спринты, Отчёты — по политике backend). |

### TC-AUTH-004. Успешный вход наблюдателя

| Поле | Значение |
|------|----------|
| **Предусловия** | Как в TC-AUTH-001. |

### TC-AUTH-005. Неверный пароль

| Поле | Значение |
|------|----------|
| **Предусловия** | Страница входа открыта. |

| **Ожидаемый результат** | Вход не выполняется. Отображается сообщение об ошибке (неверные учётные данные / ошибка входа). Пользователь остаётся на странице логина. JWT в локальном хранилище не сохраняется (или сессия не создаётся). |

### TC-AUTH-006. Несуществующий логин

| Поле | Значение |
|------|----------|

| **Ожидаемый результат** | Аналогично TC-AUTH-005: отказ во входе, понятное сообщение, без перехода в приложение. |

### TC-AUTH-007. Выход из системы

| Поле | Значение |
|------|----------|
| **Предусловия** | Пользователь авторизован (любая роль). |

| **Ожидаемый результат** | После выхода — переход на `/login`. Прямой переход на защищённые маршруты перенаправляет на страницу входа. |

### TC-AUTH-008. Доступ без авторизации

| Поле | Значение |
|------|----------|
| **Предусловия** | Сессия не создана (очищены storage/cookies или новое окно инкогнито). |
| **Шаги** | 1. Открыть `http://localhost:18080/projects` (или `/tasks`, `/reports`). |
| **Ожидаемый результат** | Редирект на `/login`. Контент приложения не отображается без токена. |

## 3. Проекты (CRUD)

### TC-PRJ-001. Просмотр списка проектов

| Поле | Значение |
|------|----------|
| **Предусловия** | Вход под пользователем с правом просмотра проектов (`admin` или `pm_sidorov`). |
| **Шаги** | 1. Открыть «Проекты».<br>2. Дождаться загрузки таблицы/списка. |
| **Ожидаемый результат** | Отображаются проекты из сидера (наименование, код, даты, ответственный и т.д. согласно UI). Нет необработанной ошибки API. |

### TC-PRJ-002. Создание проекта

| Поле | Значение |
|------|----------|
| **Предусловия** | Вход под `admin` или `pm_sidorov`; известны обязательные поля формы. |
| **Шаги** | 1. Нажать создание нового проекта (кнопка/форма по UI).<br>2. Заполнить обязательные поля валидными значениями (уникальный код, наименование, даты в допустимом формате, ответственный из списка).<br>3. Сохранить. |
| **Ожидаемый результат** | Запись создаётся; проект появляется в списке; при повторном открытии списка данные сохранены. |

### TC-PRJ-003. Редактирование проекта

| Поле | Значение |
|------|----------|
| **Предусловия** | В списке есть проект. Права на изменение. |
| **Шаги** | 1. Выбрать проект, открыть редактирование.<br>2. Изменить, например, наименование или дату.<br>3. Сохранить.<br>4. Обновить страницу. |
| **Ожидаемый результат** | Изменения отображаются после сохранения и после перезагрузки. |

### TC-PRJ-004. Удаление проекта (при наличии в UI)

| Поле | Значение |
|------|----------|
| **Предусловия** | Создан тестовый проект без критичных связей или допускается удаление по правилам БД. |
| **Шаги** | 1. Удалить проект через UI.<br>2. Подтвердить, если есть диалог. |
| **Ожидаемый результат** | Проект исчезает из списка; при ошибке FK — сообщение пользователю (не «пустой» ответ). |

### TC-PRJ-005. Валидация при создании проекта

| Поле | Значение |
|------|----------|
| **Предусловия** | Форма создания проекта открыта. |
| **Шаги** | 1. Оставить обязательные поля пустыми или ввести заведомо неверные данные (дата окончания раньше начала, дубликат кода — если проверяется).<br>2. Нажать сохранение. |
| **Ожидаемый результат** | Сохранение не выполняется; отображается сообщение об ошибке (клиентская и/или серверная валидация). |

## 9. API и инфраструктура (интеграционные)

### TC-INF-001. Проксирование `/api` через nginx

| Поле | Значение |
|------|----------|
| **Предусловия** | Docker Compose запущен. |
| **Шаги** | 1. В браузере или `curl` выполнить `POST http://localhost:18080/api/auth/login` с телом JSON `{ "login": "admin", "password": "password" }` и заголовком `Content-Type: application/json`. |
| **Ожидаемый результат** | Ответ 200 (или 2xx) с телом, содержащим токен/данные пользователя; не 404 от nginx на корректный маршрут. |

### TC-INF-002. Прямой доступ к backend (опционально)

| Поле | Значение |
|------|----------|
| **Предусловия** | Порт 8080 проброшен в `docker-compose`. |
| **Шаги** | 1. Вызвать `GET http://localhost:8080/api/projects` с заголовком `Authorization: Bearer <token>`. |
| **Ожидаемый результат** | JSON со списком проектов при валидном токене; 401 без токена. |

| **Ожидаемый результат** | Данные сохранены (если не использовали `-v`); вход и CRUD работают. |

## 10. Негативные и безопасность

### TC-SEC-001. Доступ к API без JWT

| Поле | Значение |
|------|----------|
| **Предусловия** | Известен URL защищённого endpoint, например `DELETE /api/projects/{id}`. |
| **Шаги** | 1. Выполнить запрос без заголовка `Authorization`. |
| **Ожидаемый результат** | HTTP 401 Unauthorized. |

### TC-SEC-002. Доступ с JWT другой роли

| Поле | Значение |
|------|----------|
| **Предусловия** | Получен токен `viewer`. |
| **Шаги** | 1. Вызвать операцию, разрешённую только администратору (создание пользователя, удаление проекта — по фактической политике API). |
| **Ожидаемый результат** | HTTP 403 Forbidden или эквивалентное отклонение. |

### TC-SEC-003. Хранение пароля

| Поле | Значение |
|------|----------|
| **Предусловия** | Доступ к БД (только для тестировщика/админа среды). |
| **Шаги** | 1. Выполнить `SELECT` по таблице пользователей и просмотреть поле пароля. |
| **Ожидаемый результат** | Пароль хранится в виде хеша (например, bcrypt), не в открытом виде. |
